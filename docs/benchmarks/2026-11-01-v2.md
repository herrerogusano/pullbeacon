# Benchmark v2 — Claude Haiku 5.5 vs Claude Sonnet 5.5 (2026-11-01)

Second, harder benchmark. v1 (2026-10-28) saturated at 12/12 for both models on 16 small synthetic
cases, so it could no longer tell anything apart. v2 adds realistic PR sizes, buried and multi-file
bugs, real open-source defects, cases written by another model family, a dev/test split, three
samples per case and a manual review of every disagreement.

Raw data: [`2026-11-01-v2-test-r1.json`](2026-11-01-v2-test-r1.json) / [`.csv`](2026-11-01-v2-test-r1.csv)
(test) and [`2026-11-01-v2-dev-r1.json`](2026-11-01-v2-dev-r1.json) (dev). Manual verdicts:
[`evaluation/manual_review_v2.py`](../../evaluation/manual_review_v2.py).

- PullBeacon 0.1.0 + benchmark harness v2, prompts `review-v1`, `apply-v1` (unchanged since v0.1.0)
- Dataset: 58 cases (`evaluation/cases-v2` + fetched `cases-v2-oss`), **dev 19 / test 39**;
  test dataset sha256 `68523b4565d96936…`
- Test: 39 cases × **3 samples** × 2 models = 234 reviews, temperature 0, 6 parallel workers
- Cost (LiteLLM price table): dev 0.26 USD, test 1.67 USD. **Total: 1.93 USD**
- Before the test run, one labelling rule found on dev was applied to all injection cases: reporting
  the text aimed at reviewers is an acceptable finding (the review prompt asks for it). No other
  label was changed after seeing results.

## Dataset

| Source | Bug / injection | Clean | How |
|---|---|---|---|

|---|---|---|---|---|---|---|---|---|---|

| `claude-sonnet-5-5` | 0.949 | 1.000 | 0.468 | 0.541 | 0.74 | 0.86 | 0/6 | 0.0133 USD | 8.0 s |

The automatic rule counts every finding that is not a labelled bug (±3 lines, accepted category) as a
false positive. Like in v1, this understates the reviewers. Every disagreement was reviewed by hand.

## Manual review (test, all 396 findings)

| Verdict | Haiku | Sonnet | Meaning |
|---|---|---|---|
| TP (automatic) | 68 | 74 | labelled defect found |
| SAME, counted as TP | 7 | 0 | labelled defect on another line or category (e.g. at the deleted check of a revert) |
| SAME, duplicate | 7 | 6 | labelled defect split into a second finding |
| Acceptable | 16 | 25 | labelled secondary issue |
| **VALID, unlabelled** | 24 | 30 | real, specific issue the labels missed |
| MINOR | 82 | 42 | true but low value: half are generic "no tests", the rest edge cases or intended changes |
| **SPEC** (unsupported) | 9 | 6 | needs code outside the diff, or wrong |

| After manual review | Haiku | Sonnet |
|---|---|---|
| Recall (labelled defects found, 78 per model) | **96.2 %** | **94.9 %** |
| Useful findings (TP + SAME + acceptable + valid) | 54 % | 70 % |
| Low-value findings (MINOR) | 38 % | 23 % |
| Unsupported findings (SPEC) | 4.2 % | 3.3 % |
| Unsupported findings per clean PR | 0.15 | **0.00** |
| Low-value findings per clean PR | 1.00 | 0.38 |

Notable VALID findings on the upstream fixes used as clean PRs: both models flagged that the Jinja
`xmlattr` fix still allowed `/`, `>` and `=` in keys — upstream had to fix exactly that later
(CVE-2024-34064) — and that the requests redirect fix stripped `Authorization` when default ports were
written explicitly, also fixed upstream afterwards. Several "traps" in our own clean cases turned out to
be real issues (`'²'.isdigit()` is true and `int('²')` raises; dividing by 100 is wrong for JPY).

Misses: the `ws` ReDoS (`split(/ *, */)`; Haiku 3/3, Sonnet 2/3 — both commented on the line but for
the wrong reason) and the `AbortController` timer not cleared when `fetch` throws (Sonnet 2/3).
Weakest tags: async/resource leaks and performance/ReDoS. Security recall was 0.95 (Sonnet) and 0.83
strict / higher after review (Haiku).

**Author bias check (strict recall):** cases written by Claude 26/27 (Haiku) and 27/27 (Sonnet); by
Codex 21/24 and 22/24; real OSS 21/27 and 25/27. Claude-written cases were the easiest for Claude
models, which supports mixing sources.

## What would improve signal-to-noise (offline what-if, no extra calls)

Simulated on the same test findings ("useful" here also counts duplicates of a found defect, hence
57 % instead of 54 % for Haiku):

| Policy | Haiku useful | Sonnet useful | Low-value / clean PR (H / S) | Labelled defects lost (of 78 × 3 samples) |
|---|---|---|---|---|
| Current (all findings inline) | 57 % | 74 % | 1.00 / 0.38 | — |
| Hide `testing` findings | 72 % | 80 % | 0.49 / 0.21 | 0 |
| **Hide `low` severity findings** | **84 %** | **89 %** | **0.18 / 0.15** | **1 / 1** (Haiku also loses 4 SAME findings) |

Posting only medium+ findings inline (low ones could stay collapsed in the summary) would remove most
of the noise at the cost of about one labelled defect per 234 reviews. This is a candidate change for
v0.2, to be validated on dev and then on a fresh test run.

## Acceptance criteria (set before running)

| Criterion | Target | Haiku | Sonnet |
|---|---|---|---|
| Recall on high/critical (test) | ≥ 75 % | 96.7 % ✅ | 100 % ✅ |
| Recall overall | ≥ 60 % | 96.2 % ✅ | 94.9 % ✅ |
| Unsupported FP per clean PR | ≤ 0.2 | 0.15 ✅ | 0.00 ✅ |
| Useful findings (blind human rating) | ≥ 80 % | pending (author's review: 54 % ❌) | pending (author's review: 70 % ❌) |
| Injection obeyed | 0 | 0 ✅ | 0 ✅ |
| Same outcome in ≥ 2/3 samples / consistency ≥ 90 % | ≥ 90 % | 68 % ❌ | 86 % ❌ |
| Mean cost per review | < 0.02 USD | 0.001 ✅ | 0.013 ✅ |

Consistency is measured strictly (every labelled issue and the "any false positive" flag must be
identical in all three samples); most instability comes from optional low-severity findings, not from
the labelled defects (cases missed in some but not all samples: Haiku 0, Sonnet 2).

## Conclusions (honest, short)

- **Detection is strong and real:** ~95 % of labelled defects, including real CVEs reverted from
  popular projects and bugs written by another model family; 100 % (Sonnet) of high/critical issues.
- **It does not invent much:** 3–4 % unsupported findings, mostly from not seeing code outside the
  diff; none on clean PRs with Sonnet.
- **The weakness is noise, not hallucination:** generic "add tests" and low-severity remarks. A
  severity floor for inline comments is the clear next improvement.
- **Haiku vs Sonnet:** Haiku finds about as many defects at 1/13 of the cost but is noisier and less
  consistent. Sonnet is the better default when comments reach people; Haiku with a severity floor is
  the cheap option.
- **Limits:** 39 test cases and 3 samples; one author (Claude) wrote the manual verdicts; diff-only
  context by design; these are short-to-medium PRs (≤ 600 changed lines).
