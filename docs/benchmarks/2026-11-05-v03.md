# Benchmark v0.3 — real pull requests and v3 hold-out (2026-11-05)

Written before any paid run, so that the questions and the pass criteria cannot follow the results.

## What changed since v0.2

v0.2.0 reviewed 47 times on LegalDesk, a public repository (51 findings, about 6 USD estimated).
That real use showed defects the benchmarks had not: they are small pull requests with one batch.
v0.3 changes what a batch knows and what gets reviewed: a file list per batch, prompt `review-v3`,
one summary per review, stable ids, large files split, and files without a GitHub patch rebuilt.

## Questions

**Q1. Do the false claims seen in real use go away?** Reproduce LegalDesk#77, #89 and #97 at the
commit that was reviewed, 2 samples each, with LegalDesk's own configuration.

- Pass: no finding or summary says that a file of the pull request is missing, on any sample. On
  #77 the runner `evals/phase15_golden_eval.py` is reviewed, and a part that does not fit is
  reported as partial. No summary contradicts itself.
- Also recorded: findings, and what each review costs against the same pull request on v0.2.0.

**Q2. Do the real defects found by v0.2 survive?** Same runs. On #89 and #97 the v0.2.0 findings
that were not about missing files should mostly reappear, but one sample is not enough to call a
change a loss (D-022), so differences are read by hand and reported.

**Q3. Does detection or noise get worse on the hold-out set?** v3 (46 cases, never used to tune a
change), Haiku 5.5 and Sonnet 5.5, 3 samples, the same protocol as v0.2, scored offline with the
`medium` floor.

- Pass: Sonnet and Haiku recall (strict matcher) at most 3 points below v0.2, the variation seen
  between runs, with misses reviewed by hand. Comments per review and per clean pull request not
  above v0.2's by more than the same margin.
- Most v3 cases have one batch and no file list, so this mainly tests the prompt text.

**Q4. What does the summary call cost?** Reported from the reproductions.

## What this does not answer

- Whether a human finds the summaries better. Q1 only checks contradictions and false claims.
- Whether v0.3 catches what v0.2 missed on LegalDesk#105 and #93. It is not designed to: their cause
  is outside the diff. That is the experiment that follows, and these runs give its baseline.

## Spending

Limit agreed with the owner in the plan: about 2.35 USD per v3 run, and cents to low dollars for the

in total.

## Results

Figures come from LiteLLM's pricing estimates, not from a bill. Findings marked as verified were
checked by reading the code at the reviewed commit. No blind judge was run, so the "useful comments"
share of the v3 report was **not measured** for v0.3.

### Q1. False claims: pass

Six reviews (#77, #89 and #97, 2 samples each). None says that a file of the pull request is
missing, and no summary contradicts itself.

| PR | v0.2.0 | v0.3 | Cost, v0.2.0 → v0.3 |
|---|---|---|---:|
| #77 | 1 false HIGH, runner not reviewed | No false HIGH, runner reviewed; 3 medium in each sample | 0.19 → 0.50 USD |
| #89 | 1 false "no visible tests" | That finding is gone; 1 new medium in both samples | 0.13 → 0.13 USD |
| #97 | 1 false "no visible tests", 1 low on a stale figure | The false one is gone; the low one in 1 of 2 samples | 0.24 → 0.23 USD |

On #77 one part of `tests/test_phase15_golden_eval.py` does not fit in LegalDesk's 6 batches, and
the review says so. Reviewing the runner takes the cost from 0.19 to 0.50 USD.

Verified new findings on #77, which v0.2.0 could not make because it did not see those lines:

- A mutation test can never fail: its assertion is inside `contextlib.suppress(Exception)`, which
  also swallows `AssertionError`.
- A test asserts a value against itself (`... if False else obs.called_tools`).
- `_submit` stores a session holding the access token before a call that can raise, and the caller
  only deletes it once `_submit` has returned.

The new medium on #89 (an exemption in a change-set gate that does not check which attribute it
relies on) is a fair remark, with confidence 0.3-0.4. Its effect in practice was not established.

Wart: two summaries say "Reviewers found", because the parts are described as separate reviews.

### Q2. Real defects found by v0.2: no loss seen

v0.2.0 reported little else on these pull requests: the stale figure on #97 reappears in 1 of 2
samples, within normal variation.

### Q3. Hold-out set: Sonnet passes, Haiku does not meet the criterion as written

| v3, 138 reviews, 3 samples | Haiku v0.2 | Haiku v0.3 at 4096 | Haiku v0.3, large cases at 8192 | Sonnet v0.2 | Sonnet v0.3 |
|---|---:|---:|---:|---:|---:|
| Failed reviews | 1 | 4 | 0 | 0 | 0 |
| Recall, strict matcher | 91.4 % | 86.4 % | **84.0 %** | 95.1 % | **96.3 %** |
| Comments per review, floor `medium` | 0.86 | 0.79 | 0.85 | 0.83 | 0.88 |
| Comments per clean PR, floor `medium` | 0.18 | 0.16 | 0.26 | 0.21 | 0.26 |
| Cost per review, USD | 0.0012 | 0.0011 | 0.0011 | 0.0158 | 0.0153 |

**Sonnet passes.** Recall rises, and comments per clean pull request go from 0.21 to 0.26.

**Haiku's strict recall is 7.4 points below v0.2, over the 3-point limit written above.** Read by
hand, 12 of the 13 misses in that column are the labelled defect reported a few lines away, so
the model found it and the matcher did not count it (examples: `moment` at line 79 for a label at
73, `slot_booking` at 22 for labels at 26 and 37). One is a real miss in one sample
(`tornado_cookie_unquote_quadratic`, sample 0). This does not change the result of the criterion,
which is recorded as failed for Haiku. Its comments per clean pull request also rise, from 0.18 to
0.26; part of that is reviews that used to fail now completing and commenting. Whether those
comments are useful was not measured.

**A regression found by this run.** v0.2.1 (PR #23) stopped retrying cut-off answers, assuming a
retry would be cut off too. On Haiku's 18 reviews of large cases, v0.2 had totals up to 8,047 tokens,
from retries that succeeded, and 1 failure; without the retry, 4 failed. PR #31 raises the default
limit to 8192: the same 18 reviews had no failures and used at most 4,104 tokens. The large cases in
the fourth column were rerun on the new limit; the others were not, because it does not affect them.

### Q4. Cost of the summary call: not itemised

The report only has totals per review. Multi-batch reviews have one more call, whose input is only
summaries and titles, and on #89 and #97 the total did not rise visibly.

### Experiment: context outside the diff

Agreed criterion, before running: adopt it only if it catches #105 and #93 without raising noise.
**Not met, so it is not in v0.3.** No noise run was made, since detection already failed.

| Variant | #105 (fix that could never act) | #93 (edit that blocks the release pipeline) |
|---|---|---|
| Current v0.3 (baseline) | 0 of 2 | 0 of 2 |
| A first call picks up to 5 files outside the diff | 0 of 2 | 0 of 1; another run was cut off at its 512-token limit |
| Whole changed files as context | **1 of 2** | Not run: the cause is in a file the pull request does not touch |

- **The lookup does not find the right files.** On #93 it read `scripts/phase15_changeset_preview.py`
  and other templates, not `scripts/deploy_release.py`. Nothing in the diff points to it.
- **The whole-file variant found the real defect of #105** in one sample: the production
  `ConverseAnswerWriter.write` raises before the new handler runs. This is the bug that made the fix
  inert in real use.
- **These costs say little about a proper version.** The runs cost 0.55-0.66 USD against 0.03 for a
  normal #105 review, because the prototype counts the context against the batch budget: the files
  used it up, the diff was cut into 1,000-character batches (7 calls) and they were resent each time.
  Parts of the diff also went unreviewed, so the 1 of 2 was measured under poor conditions. The labels
  also call those files "from the base branch" when they are from the head.

Open question for a later version: whole changed files, built properly, measured on cost, on noise
and on more than this one case. n=2 proves nothing yet.

## Limits

- 2 samples per real pull request, all from one project, read by the author of the change.
- No blind judge on v0.3, and no human rating.
- v3 cases rarely have more than one batch, so the file list and the summary call are only tested
  by the reproductions.
- The reproductions use LegalDesk's current configuration, which may differ from the one at the time
  of each original review.
